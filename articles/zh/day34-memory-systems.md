# Day 34: 记忆系统 — 智能体如何记住、遗忘与持续学习

> **核心问题**: 为什么 LLM 智能体记不住昨天发生的事？工程师如何构建跨会话的持久记忆系统？

---

## 开篇

想象你每周都和同一个人喝咖啡。每次见面，TA 都从头自我介绍、问你同样的工作问题，到下周就把你说的全忘了。这会很让人崩溃——但这恰恰是大多数 LLM 智能体的默认行为。

LLM 的上下文窗口就是它的"工作记忆"。它保存着对话中当前出现的所有内容，直到触及 token 上限（根据模型不同，可能是 128K、200K 或 1M）。一旦对话结束，这些记忆就彻底消失。下一次会话从零开始。

记忆系统就是工程师对这一根本局限的回应。它让智能体能够跨会话持久保存信息、按需检索相关上下文、逐步积累知识——就像人类通过反复经历建立长期记忆一样。

本文覆盖智能体记忆的三个层次、支撑长期存储的基础设施（向量数据库、知识图谱），以及 2025–2026 年间涌现的实用框架。

## 1. 智能体记忆的三层架构

#### 直觉：你大脑的记忆系统

想想你工作日的记忆是怎么运作的。**工作记忆**保存你当下正在思考的内容——正在读的句子、刚算出的数字。**短期记忆**追踪今天的会议和任务。**长期记忆**存储同事的名字、项目的历史、几个月前学到的教训。

智能体记忆遵循类似的三层结构：

![图 1：三层记忆层次结构](./images/day34/memory-hierarchy-tiers.png)
*图 1：记忆金字塔——工作记忆（快速、小容量、易失）在顶部，长期记忆（慢速、大容量、持久）在底部。信息通过压缩向下流动，通过检索向上返回。*

### 1.1 工作记忆（上下文窗口）

这是 LLM 的即时上下文——prompt 中当前出现的每个 token。它是最快、最精确的记忆形式，因为模型可以直接关注每个 token。但它也是最有限、最昂贵的。

| 属性 | 详情 |
|------|------|
| 容量 | 4K–1M tokens（取决于模型） |
| 延迟 | 即时（已在上下文中） |
| 持久性 | 无——会话结束即清除 |
| 成本 | 与 token 数量成正比（按输入定价） |

核心矛盾：把所有东西塞进上下文窗口虽然精确，但代价高昂且最终会触及上限。这就是我们需要其他层的原因。

### 1.2 短期记忆（会话缓冲区）

这是单次会话中的对话历史。大多数智能体框架保留最近消息的滑动窗口，有时对较早的对话进行摘要。

#### 直觉：侦探的笔记本

侦探办案时会随身带个笔记本记录当天的线索——他不会把三年悬案的每个细节都背下来，只记当下相关的。案子结了，笔记本放进档案柜。这就是短期记忆：在会话内有价值，但不是最终归宿。

常见策略：
- **滑动窗口**：保留最近 N 条消息原文
- **摘要缓冲**：对较早消息进行摘要，保留最近消息原文
- **Token 预算**：分配固定 token 预算，用最相关的近期上下文填满

### 1.3 长期记忆（持久存储）

信息在这里跨会话存活。这是最大的层级，但访问速度也最慢，因为需要经过检索步骤才能注入工作记忆。

长期记忆通常采用两种存储范式之一：
- **向量数据库**：存储事实、文档和对话的嵌入向量；通过相似度搜索检索
- **知识图谱**：存储结构化的实体和关系；通过图遍历检索

我们将在第 3 节和第 4 节详细探讨这两种方案。

## 2. 为什么记忆很难

为智能体构建记忆不仅仅是存储数据——它关乎决定存*什么*、*什么时候*检索、以及*如何*保持信息的新鲜度。

### 2.1 存储问题：保留什么？

处理成千上万对话的智能体会产生海量文本。存一切太贵，存太少又意味着遗忘重要事实。核心挑战是**抽取**：从原始对话中提取有用的事实。

例如，从这段对话中：

> 用户："我上周刚搬到柏林。天气比新加坡冷多了。"

好的记忆系统应该提取：
- **事实**：用户从新加坡搬迁到柏林（附带时间戳）
- **偏好上下文**：用户了解两个城市的气候
- **不值得存储**：原话文字本身——只要结构化信息

### 2.2 检索问题：当下什么最相关？

即使存储完美，检索也是瓶颈。当用户问"你推荐什么餐厅？"，智能体需要回忆饮食限制、过往偏好和位置——但不需要之前每段对话的全文。

这就是大规模的**大海捞针**问题。检索质量直接决定长期记忆有多大用处。糟糕的检索意味着智能体要么遗漏关键上下文，要么用不相关信息淹没上下文窗口。

### 2.3 新鲜度问题：过时的记忆

#### 直觉：过时的通讯录

想象你的手机通讯录永远不让删除或更新条目。朋友三年前就搬家了，但旧地址还在。你不断把邮件寄到错误的地方。智能体记忆有同样的问题——如果你存储了"Alice 偏好 Python"但她六个月前转到了 Rust，过时的记忆比没有记忆更糟。

正如 [Mem0 的《AI 智能体记忆现状 2026》报告](https://mem0.ai/blog/state-of-ai-agent-memory-2026)（2026 年 5 月）所指出的，长期运行的智能体会基于过时数据行动，除非记忆系统包含明确的**时间推理**机制——理解"当前偏好"和"上月偏好"可能不同。

### 2.4 Token 预算问题

每条检索到的记忆都会消耗上下文窗口的 token。如果智能体有 128K token 的上下文，检索了 50K token 的"相关"记忆，留给实际任务的空间就很少了。记忆系统必须精打细算——在紧张的 token 预算内返回*最有用*的信息。

## 3. 向量数据库：长期记忆的主力

### 3.1 向量存储的工作原理

#### 直觉：按意义而非字母排列的图书馆

想象一座图书馆，书不是按作者姓氏排列，而是按*意义*排列。烹饪类的书放在其他烹饪书附近，但也在化学书（共享概念）和文化书（饮食传统）旁边。如果你要"关于做面包的书"，图书管理员走到正确的区域，抽出最相关的几本。

这本质上就是向量数据库的工作方式。每条存储的信息（一个事实、一个文档片段、一段对话摘录）都被嵌入模型转换为高维向量（通常 256–3072 维）。在这个空间中距离相近的向量代表语义相似的内容。

![图 2：向量数据库架构](./images/day34/vector-database-architecture.png)
*图 2：索引管道（左）将原始数据转换为嵌入向量，用 HNSW 索引存储。查询管道（右）将用户问题嵌入，执行近似最近邻搜索，返回最相似的结果。*

### 3.2 检索管道

检索过程分三步：

**第一步——嵌入查询。** 使用与索引时相同的嵌入模型，将用户问题转换为向量。

**第二步——近似最近邻（ANN）搜索。** 与其将查询向量与每个存储向量逐一比较（复杂度 O(n)），ANN 算法如 **HNSW（分层可导航小世界图）** 在 O(log n) 时间内找到近似最近邻。这以少量精度换取了巨大的速度提升。

**第三步——排序并返回 Top-K 结果。** 检索到的候选结果通过余弦相似度（或点积）评分，返回最相关的前 K 个结果。

相似度评分的关键公式：

$$
\begin{aligned}
\text{sim}(q, d) = \frac{q \cdot d}{\|q\| \cdot \|d\|}
\end{aligned}
$$

其中 **q** 是查询向量，**d** 是文档向量。结果范围从 -1 到 1，1 表示方向完全相同。

### 3.3 向量数据库全景（2026）

市场已形成几个强有力的选择，各有不同的取舍：

| 数据库 | 类型 | 最适合 | 延迟（1000 万向量） | 规模上限 |
|--------|------|--------|---------------------|----------|
| **Pinecone** | 托管无服务器 | 生产团队，零运维 | ~16ms p50 | 数十亿 |
| **Weaviate** | 开源 + 云 | 混合搜索（关键词 + 向量） | ~16ms p99 | 数百万 |
| **pgvector** | PostgreSQL 扩展 | 已有 Postgres 的用户 | ~25-40ms p99 | ~5000万/节点 |
| **Chroma** | 开源，轻量 | 原型开发，本地使用 | 小规模快 | ~1000-5000万 |
| **Milvus** | 开源，分布式 | 十亿级规模，GPU 加速 | ~18ms p99 | 数十亿 |

**2026 年关键进展：**
- **Milvus 2.6**（2026 年初在 [Zilliz Cloud](https://zilliz.com/blog/milvus-2-6-ga-on-zilliz-cloud) GA）：BM25 优化全文 + 向量混合搜索，在某些数据集上比 Elasticsearch 快 7 倍；分层存储（内存、本地 SSD、对象存储）
- **Weaviate Agent Skills**（2026 年 2 月）：面向编程智能体的开源工具，用于生成 Weaviate 工作流，减少 RAG 管道调试时间（[GlobeNewsWire 公告](https://www.globenewswire.com/news-release/2026/2/21/3242244/0/en/weaviate-launches-agent-skills-to-empower-ai-coding-agents.html)）
- **pgvector** 成熟度提升：`halfvec` 量化将维度存储为 16 位浮点数，存储减半但召回率损失极小；支持 Matryoshka 表示学习（MRL）动态截断维度

#### 直觉：选择向量数据库就像选车

Pinecone 是出租车——你不用开，只管坐。pgvector 是你已经有的车——能用、熟悉，但不赢比赛。Milvus 是货运卡车——买菜大材小用，运集装箱不可或缺。Chroma 是自行车——在小区里完美，不适合长途。根据你的实际旅程来选。

### 3.4 嵌入模型：向量搜索的引擎

检索质量很大程度上取决于嵌入模型。2026 年的主要选择：

| 模型 | 维度 | 上下文 | 价格（每百万 token） | 优势 |
|------|------|--------|---------------------|------|
| OpenAI text-embedding-3-large | 3072（MRL: 256–3072） | 8,192 | $0.13 | 通用英文，MRL 支持 |
| Voyage AI voyage-4-large | 2048（MRL: 256–2048） | 32,768 | ~$0.08 | MoE 架构，代码检索 |
| Google Gemini Embedding | 3072 | 8,192 | ~$0.05 | 首个多模态（文本+图像+视频） |
| 阿里 text-embedding-v4 | 2048 | 8,192 | ~$0.07 | 多语言，推荐场景 |

**Matryoshka 表示学习（MRL）** 由 OpenAI 于 2023 年末首次引入，现已广泛采用。它允许在查询时截断嵌入维度（例如只使用 3072 维中的 256 维），质量损失极小，大幅降低大型集合的存储成本。

## 4. 超越向量：知识图谱记忆

### 4.1 为什么向量不够

向量数据库擅长*语义相似度*——找到与查询"意思接近"的内容。但在以下场景表现不佳：
- **关系推理**："谁把 Alice 介绍给 Bob 的？"需要理解实体关系，而非相似度
- **时间查询**："Alice 搬家*之前*偏好什么？"需要时间感知存储
- **多跳推理**："构建项目 X 的团队用了什么工具？"需要沿关系链追踪

#### 直觉：通讯录 vs 社交网络

向量数据库就像通讯录——存储每个人的信息，能找到相似的人。知识图谱就像社交网络——存储*谁认识谁*以及*他们什么关系*。你需要两个视角才能完整理解一个社区。

### 4.2 Graphiti 与时间感知知识图谱

**Graphiti** 由 [Zep AI](https://www.getzep.com/product/open-source/) 开发，于 2025 年初开源，是专门为智能体记忆设计的时间感知知识图谱构建框架。其架构论文（[arXiv:2501.13956](https://arxiv.org/abs/2501.13956)）引入了新方法：

1. **片段摄取**：每段对话或文档存储为"片段"（Episode）节点
2. **实体提取**：LLM 提取命名实体（人物、概念、物品），创建实体节点
3. **关系边**：LLM 识别实体间的关系，附带时间有效性（开始日期、结束日期）
4. **无损设计**：每个事实都可追溯到来源片段，支持溯源追踪

这意味着当 Alice 的偏好从 Python 变为 Rust 时，图谱存储*两条*事实及不同的时间范围，查询可以指定时间上下文。

## 5. 实践中的记忆框架

### 5.1 Letta（前身 MemGPT）

[Letta](https://www.letta.com/blog/agent-memory) 最初由加州大学伯克利分校的研究者以 MemGPT 论文形式发表在 ICLR 2024，采用了**操作系统启发**的智能体记忆方法。这个名字是对操作系统通过虚拟内存、分页和缓存管理内存的致敬。

三层架构：
- **核心记忆**：始终在上下文中（类似内存）。存储用户画像、当前任务状态和关键事实。智能体可以*直接编辑*——本质上是上下文窗口内的结构化便签板。
- **回忆记忆**：可搜索的对话历史（类似磁盘缓存）。智能体可以通过搜索查询过往交互。
- **归档记忆**：长期存储（类似硬盘）。智能体可以插入和检索信息，底层使用向量数据库（PostgreSQL + pgvector 或 Chroma）。

2025–2026 年关键进展：
- **Letta Code App**（2026 年 3 月）：记忆优先的编程智能体，本地运行并随时间从交互中学习
- **Conversations API**（2026 年 1 月）：智能体可在并行用户体验间维护共享记忆
- **睡眠时计算（Sleep-time compute）**：异步记忆管理，在不阻塞主对话的情况下处理和整合记忆

### 5.2 Mem0

[Mem0](https://mem0.ai/) 在 2025 年 10 月完成 2400 万美元 A 轮融资，定位为**通用记忆层**，任何智能体都可即插即用。架构比 Letta 更简洁：

1. **摄取**：输入对话、文档或任何文本
2. **抽取**：LLM 提取结构化事实（而非原始文本）
3. **存储**：事实以向量嵌入 + 轻量级图层（追踪实体关系）的形式存储
4. **检索**：查询时，相关事实被注入智能体的上下文

2026 年关键更新：
- **2026 年 4 月算法发布**：单次遍历分层抽取与多信号检索，显著提升 token 效率（[Mem0 博客，2026 年 5 月](https://mem0.ai/blog/state-of-ai-agent-memory-2026)）
- **时间推理**：理解事实有时间范围，当前偏好和历史偏好可能不同
- 支持 **20 个向量存储后端**，包括通过 `@mem0/openclaw-mem0` 与 OpenClaw 的集成

### 5.3 Zep（Graphiti）

[Zep](https://www.getzep.com/product/open-source/) 采用了结构上最雄心勃勃的方案。它不使用扁平的向量存储，而是使用开源 [Graphiti](https://github.com/getzep/graphiti) 库构建**时间感知知识图谱**。

| 特性 | Letta | Mem0 | Zep |
|------|-------|------|-----|
| 架构 | 操作系统启发三层 | 抽取 + 图层 | 时间感知知识图谱 |
| 存储 | pgvector / Chroma | 20+ 后端 | Neo4j + 向量存储 |
| 时间感知 | 有限 | 2026 年 4 月新增 | 核心设计（自 2025 年起） |
| 自编辑记忆 | 是（核心记忆） | 否 | 部分（通过图更新） |
| 最适合 | 复杂智能体工作流 | 简单即插即用 | 关系密集领域 |
| 开源 | 是 | 是 | 是（Graphiti） |

## 6. 构建一个简单的记忆系统

下面是一个使用 Python 和 Chroma 的最小但可用的记忆系统（用于本地原型开发）：

```python
import chromadb
from datetime import datetime

class AgentMemory:
    """简单的两层记忆：工作记忆（上下文内）+ 长期记忆（向量数据库）。"""
    
    def __init__(self, collection_name="agent_memory"):
        self.client = chromadb.PersistentClient(path="./memory_db")
        self.collection = self.client.get_or_create_collection(
            name=collection_name,
            metadata={"hnsw:space": "cosine"}  # 使用余弦相似度
        )
        self.working_memory = []  # 上下文内事实
    
    def store(self, text: str, metadata: dict = None):
        """将事实存入长期记忆。"""
        if metadata is None:
            metadata = {}
        metadata["timestamp"] = datetime.now().isoformat()
        
        self.collection.add(
            documents=[text],
            metadatas=[metadata],
            ids=[f"mem_{datetime.now().timestamp()}"]
        )
    
    def retrieve(self, query: str, top_k: int = 5):
        """为给定查询检索相关记忆。"""
        results = self.collection.query(
            query_texts=[query],
            n_results=top_k
        )
        return results["documents"][0], results["metadatas"][0]
    
    def get_context(self, query: str, token_budget: int = 2000):
        """获取格式化的上下文，用于注入 LLM prompt。"""
        docs, metas = self.retrieve(query, top_k=10)
        
        context_parts = []
        current_tokens = 0
        # 粗略估算：1 token ≈ 4 个字符
        for doc, meta in zip(docs, metas):
            est_tokens = len(doc) // 4
            if current_tokens + est_tokens > token_budget:
                break
            timestamp = meta.get("timestamp", "unknown")
            context_parts.append(f"[{timestamp}] {doc}")
            current_tokens += est_tokens
        
        return "\n".join(context_parts)

# 使用示例
memory = AgentMemory()

# 存储从对话中提取的事实
memory.store("用户偏好所有应用使用暗色模式")
memory.store("用户时区是 Asia/Singapore (UTC+8)")
memory.store("用户正在准备 NLP 方向的博士申请")

# 之后在新会话中检索相关上下文
context = memory.get_context("我应该用什么显示设置？")
print(context)
# 输出: [2026-05-18T08:00:00] 用户偏好所有应用使用暗色模式
#       [2026-05-17T14:30:00] 用户时区是 Asia/Singapore (UTC+8)
```

这是有意保持简洁的——生产系统会加入去重、LLM 事实抽取、实体消歧和时间元数据。

## 7. 检索的取舍全景

## 8. 常见误解

### ❌ "把所有东西塞进上下文窗口就行了"

既然模型已支持 200K–1M token，你可能会觉得外部记忆没必要。但是：
- **成本**：按 $3/百万输入 token 算，1M token 的上下文每次请求就要 $3
- **延迟**：处理 1M token 需要秒级而非毫秒级
- **大海捞针**：塞入的上下文越多，模型找到相关内容的难度越大。我们在 Day 19 讨论过"迷失在中间"现象——模型难以利用长上下文中部的信息。

### ❌ "向量数据库解决一切问题"

向量搜索找到的是*相似*内容，不一定是*相关*内容。如果用户问"今晚该做什么菜？"，检索到"鸡肉阿斗波"的食谱仅仅因为它与"烹饪"语义相似，就搞错了重点——你应该检索的是*饮食限制*和*可用食材*。混合方法（向量 + 关键词 + 元数据过滤 + 图关系）始终优于纯向量搜索。

### ❌ "记忆越多越好"

每条检索到的记忆都要消耗 token。用 50 条"相关"记忆淹没上下文窗口，留给推理的空间就很少了。记忆系统的艺术在于**精准**——返回 5 条最有用的事实，而非 50 条最相似的。

## 9. 前沿：快速变化的领域（2025–2026）

记忆系统领域正在快速演进：

1. **Agentic Memory（AgeMem）**——2026 年 1 月的论文（[arXiv:2601.01885](https://arxiv.org/abs/2601.01885)）提出统一框架，让智能体*学习*何时存储、检索和遗忘，而非遵循固定规则。在五个长周期基准测试中表现一致提升。

2. **LongMemEval-V2**——2026 年 5 月的基准测试（[arXiv:2605.12493](https://arxiv.org/html/2605.12493)）评估智能体的长期记忆，目标是创造"有经验的同事"——随时间积累专业知识的智能体，而不只是存储事实。

3. **Mem0 2026 年 4 月算法**——单次遍历分层抽取与多信号检索，加入时间推理，在提升检索质量的同时显著降低 token 成本（[Mem0 记忆现状 2026 报告](https://mem0.ai/blog/state-of-ai-agent-memory-2026)）。

4. **Letta Code App（2026 年 3 月）**——记忆优先的编程智能体，本地运行并随时间构建个性化知识，证明记忆不仅对聊天机器人有用——对开发者工具也是变革性的。

5. **AgentRunbook-C**——来自 LongMemEval-V2 团队的新方法：不将检索压缩为固定的向量搜索管道，而是将轨迹存储为文件，用编程智能体在查询时搜索、检查和选择证据。

6. **ReMe（Remember Me, Refine Me）**——开源记忆管理工具包（[GitHub](https://github.com/agentscope-ai/ReMe)），支持多种向量存储后端、LLM 提供商和嵌入模型，强调模块化组合。

## 思考题

1. 如果一个智能体同时拥有向量数据库和知识图谱作为长期记忆，它应该在什么时候查询其中一个而非另一个？哪些类型的问题各自更擅长回答？

2. "新鲜度问题"意味着过时的记忆可能比没有记忆更糟。你会如何设计一个优雅处理随时间变化的事实的记忆系统——而不需要用户显式纠正每一条过时细节？

3. Token 预算迫使做出艰难的取舍：检索的上下文越多，留给推理的空间越少。如果你有 2000 token 的记忆检索预算，你会如何在不同类型的记忆（用户偏好、对话历史、事实知识、任务上下文）之间分配？

## 总结

| 概念 | 一句话解释 |
|------|-----------|
| 工作记忆 | 上下文窗口——快速、精确，但易失且有限 |
| 短期记忆 | 会话对话缓冲——会话内持久，会话后清除 |
| 长期记忆 | 向量数据库/知识图谱——跨会话持久，需要检索 |
| 向量数据库 | 存储嵌入向量进行语义相似度搜索；HNSW 索引实现快速 ANN |
| 知识图谱 | 存储带时间元数据的实体和关系，用于关系推理 |
| Letta（MemGPT） | 操作系统启发三层记忆，带自编辑核心记忆 |
| Mem0 | 通用记忆层，带抽取、图和注入管道 |
| Zep（Graphiti） | 时间感知知识图谱，带基于片段的溯源追踪 |
| HNSW | 分层可导航小世界图——主流的 ANN 索引算法 |
| MRL | Matryoshka 表示学习——可截断嵌入向量以降低成本 |

**核心要点**：记忆系统是区分无状态聊天机器人和持久智能体的关键。工程挑战不仅仅是存储——还在于决定保留什么、遗忘什么，以及如何在恰当的时间找到恰好的上下文。最好的系统结合向量数据库的语义搜索与知识图谱的关系推理，包裹在智能的抽取和检索逻辑中，同时尊重 token 预算和时间上下文。
